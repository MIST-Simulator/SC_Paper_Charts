These files cannot be regenerated by `run_T2.py` because they require either
physical H100 nodes running vLLM, the separate Vidur simulator, or a physical

**Camera-ready Fig. 6(a) is mislabelled as "Llama3-70B".** The published
figure image (`MIST_SC26_source/figures/image/individual_step_validation.pdf`)
labels the two rows "Llama3-70B / H100xTP4" and "Llama3-70B / H100xTP8", but
the paper body says otherwise -- §4.2 states "vLLM running Llama-2-70B on
H100x8" -- and the underlying data files above are unambiguously Llama-2-70B
(`Llama-2-70b-hf_NVIDIA_H100_{4,8}.csv`; the original notebook's own model
dict key was also `'Llama3-70B'`, i.e. the mislabelling predates this port).
This reproduction uses the correct "Llama-2-70B" label in `run_T2.py` /
`plot_T2.py`, matching the data and the paper text; the discrepancy with the
camera-ready image is intentional and documented here rather than silently
matched.

**MIST's model for this figure is the ML-based per-step predictor, not the
GenZ analytical roofline.** The paper's §4.1.1 ("LLM Client HW Executor")
defines MIST's per-step runtime model as an ensemble of regressors trained
on profiled vLLM data, and §4.2's validation subsection is explicitly scoped
to "our ML-Based LLM Cluster Modeling (§4.1.1)". `run_T2.py` therefore uses
`mist.Platforms.vllm_platform.vLLMPlatformConfig` (lookup + RandomForest
ensemble over profiled vLLM data) pointed at the two `vllm_step_runtime_*.csv`
files above as "MIST", not `mist.Platforms.platforms.PlatformConfig` (the
GenZ analytical path — see "Known upstream issues" below for why that path
gives a very different, much worse number, and why that's expected and not
a bug in this reproduction).

Because vLLMPlatformConfig's near-exact lookup and its RandomForestRegressor
are fit directly on the profiled CSV, evaluating them on rows drawn from
that same CSV is tautological unless those exact rows are excluded from
training first. `run_T2.py` therefore does a seeded, deterministic **held-out
group split**: for each (hardware, stage), it groups rows by exact
`(total_batches, total_tokens)` — the same key vLLMPlatformConfig's own
lookup matches on — and holds out a whole `--holdout-frac` (default 0.2) of
those groups. `vLLMPlatformConfig` is instantiated on a temp CSV containing
only the non-held-out rows, so the near-exact lookup can never find a
held-out row's configuration and every held-out row is scored purely by the
(also held-out) regressor.

Because the real-vLLM and Vidur runs used their own live schedulers, the two
CSVs do not share the same step boundaries — Vidur's own scheduling
decisions produce a different number of rows than vLLM's. Vidur — itself an
ML predictor trained on profiling data, per the paper — is evaluated with
the *same* held-out-group protocol applied to its own CSV: a small
RandomForestRegressor (`sklearn.ensemble.RandomForestRegressor`, seeded) is
fit on Vidur's `(batches, tokens, kv_length, attn_size) -> Time` pairs
**excluding** the same held-out groups used for the real-vLLM split, then
evaluated on the same held-out real-vLLM rows MIST is scored on — so the two
series are compared on an apples-to-apples, no-leakage basis.

## Known upstream issues (informational — not the mechanism used above)

While investigating a first (incorrect) draft of this reproduction that used
`PlatformConfig.get_chunked_time()` (the GenZ analytical roofline) as
"MIST" for Figure 6(a), two independent upstream issues were found. Neither
affects the numbers above (which use `vLLMPlatformConfig`, per the paper's
own description of Fig. 6(a)'s methodology), but both are real and worth
tracking:

1. **`PlatformConfig` hardcodes `bits='fp8'`.** `mist/Platforms/platforms.py`
   passes `bits='fp8'` into every `chunked_moddeling`/`System(...)` call
   (lines 78, 276, 323, 361, 379), and `PlatformConfig.__init__` exposes no
   dtype parameter to override it. Manually forcing `bf16` on one sample
   request (Llama-2-70B, TP4, 391-token prefill) roughly doubled the
   predicted latency (12.6 ms → 23.4 ms fp8→bf16, vs. 39.1 ms measured),
   which plausibly explains most of the ~2-3x systematic underprediction
   this path produces against real bf16/fp16 vLLM runs. This path is what
   the paper uses for *hypothetical, unprofiled* hardware in §5.1 (Etched,
   GB300, TPUv7) where no profiled vLLM data exists to fit an ensemble —
   it was never the claimed basis for Fig. 6(a).
2. **`PlatformConfig(device="h100_sxm", ...)` (the profiled-ops/`System`
   path) crashes in this environment's GenZ checkout** with
   `AttributeError: type object 'GEMMQuantMode' has no attribute
   'bfloat16'` in `GenZ/db.py` (`bits_to_gemm_quants` maps `'bf16' ->
   GEMMQuantMode.bfloat16`, but the enum only defines `float16`). This
   blocks the more detailed profiled-hardware device path entirely,
   independent of the `fp8` issue above.

## KV cache retrieval latency baseline (Figure 6b)

`fio_retrieval_latency.csv` — sequential-read latency of a KV cache block,
measured with [`fio`](https://fio.readthedocs.io/) directly against the
block device / RAM (`--rw=read --ioengine=psync --direct=1`, single job),
sweeping block size 256 KB → 1 GB. Reproduces the `avg` completion latency
reported by `fio`'s `lat (usec)` histogram.

| Device | Machine | Notes |
|--------|---------|-------|
| `DDR4` | Linux workstation, DDR4 DRAM accessed as a block device (`/dev/shm`-backed or equivalent) | Values ported from `GenA_Paper_charts/Validation/2.ASPLOS/read_latency/combined_retreival_latency_plot.py` (`empirical_latency` array, DDR4 section). |
| `NVMe SSD` | Same workstation, local NVMe SSD | Values ported from the same script's NVMe section; matches `GenA_Paper_charts/Validation/2.ASPLOS/read_latency/fio_latency_data_macbook.csv` (256 KB–1 GB rows). |

These numbers were previously hardcoded as inline numpy arrays inside the
plotting script; they are vendored here as data instead, exactly as
measured — `run_T2.py`/`plot_T2.py` never edit them. The `fio` command line
used to collect them is `GenA_Paper_charts/Validation/2.ASPLOS/read_latency/fio_latency_sweep.sh`.
Reproducing them requires the original physical DDR4/NVMe hardware.

The MIST curve for this panel is *not* vendored: `run_T2.py` computes it by
calling MIST's own KV-retrieval cost model
(`mist.Platforms.memory_platform.SingleCacheConfig.get_retrieval_time`, via
`MemoryCacheConfig.get_KV_cache_time`) with representative DDR4/NVMe device
parameters (typical CAS-latency-scale lookup latency and sequential
bandwidth), for a synthetic Llama-3-70B (`meta-llama/llama-3.1-70b`, the
closest available GenZ config — 160 KB/token KV cache, matching the
notebook's stated assumption) KV cache of the same token-equivalent sizes as
the swept block sizes.
