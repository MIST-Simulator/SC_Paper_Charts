# T1 validation baselines

These files back Fig. 4(a-d): the measured/third-party numbers `plot_T1.py`
overlays on top of MIST's own output. **None of them can be regenerated by
this repository** — they require either the original physical hardware
(vLLM) or a separate simulator installation (Vidur, LLMServingSim2.0). They
were copied verbatim from
`GenA_Paper_charts/Validation/{3.ISCA26,4.SC26/SimulatorComparision}/` in
the MIST paper's working repository, which holds the exact experiment
scripts/configs that produced them.

By default, `run_T1.py` replays the two `sharegpt_replica_*.csv` files
below as its input workload — see "Fixed validation trace vs.
`--resample-sharegpt`" further down for why that matters.

## Axis-label bug in the camera-ready figure (fixed in this reproduction)

The camera-ready Fig. 4(a,b) y-axis is labeled "Latency (ms)", but the
plotted quantity in both panels is **seconds**, not milliseconds — e.g.
panel (a) tops out around 40 while `run_T1.py` reports a mean L40S e2e
latency of 12.8s, and panel (b) tops out around 15 with a mean H100 e2e
latency of 2.9s; both are consistent with seconds, not ms. Panel (c) is
correctly labeled "Latency (sec)". This mislabel exists in the published
paper's figure (it isn't something this reproduction introduced), but
`plot_T1.py` here corrects it: all three latency panels now read
"Latency (sec)". We verified there is no unit bug in the underlying data
or a double conversion hiding behind the wrong label — every source is
seconds already, once, end to end:
- `run_T1.py`: `mist_e2e_sec = (finished_time_ms - arrival_time_ms) / 1000.0`
  (MIST's internal clock is milliseconds; dividing once yields seconds).
- `vllm_*.json`: `e2els`/`e2el` are vLLM benchmark_serving.py's native
  per-request seconds; used as-is.
- `vidur_*_request_metrics.csv`: `request_e2e_time` is Vidur's native
  seconds; used as-is.
- `llmservingsim_*_result.csv`: `latency` is nanoseconds; divided by `1e9`
  once to seconds.
- `vllm_tpu_llama31-8b.json`: `last_token_time - sent_time` are Unix
  timestamps in seconds; the difference is seconds, used as-is.

## Measured accuracy vs. the paper's and the AD's claims

Running `run_T1.py` in its default (fixed-trace) mode gives the following
per-platform sorted-distribution MAE between MIST and the real vLLM
measurement:

| Platform | MIST vs. vLLM MAE |
|---|---|
| L40S:TP2 (Qwen3-32B) | 11.46% |
| H100:TP8 (Llama3-70B) | 6.51% |
| TPUv6e (Llama-3.1-8B) | 8.26% |

The paper body (§4.2) states MIST achieves "less than 2% average error
across different combinations of HW and models." These measured numbers
do not support that claim — they are 3-6x higher than 2% on every
platform. They **do** fall inside the artifact description (AD)
appendix's stated expectation of "approximately 5-10% mean absolute error
across the three validation platforms" (L40S is slightly above that band,
H100 and TPUv6e are within it). So this reproduction is self-consistent
with the AD's own stated expectation, but does not reproduce the paper
body's stronger <2% claim. We did not tune the workload, model configs, or
metric to chase 2% — these are the numbers `run_T1.py` produces against
the fixed validation trace as vendored.

## Fixed validation trace (default `run_T1.py` input)

| File | What it is |
|------|-----------|
| `sharegpt_replica_5qps_tpu_h100.csv` | The exact 100-request ShareGPT trace (arrival time, prompt tokens, output tokens) replayed against real vLLM to produce `vllm_h100_llama3-70b_tp8.json` and `vllm_tpu_llama31-8b.json`, and against Vidur to produce `vidur_h100_llama3-70b_tp8_request_metrics.csv`. Target rate: 5 req/s. Used as-is for both the H100 and TPU platforms (the original notebook replayed this identical sample against both). |
| `sharegpt_replica_2.5qps_l40s.csv` | The equivalent fixed trace used for the L40S real-vLLM run (`vllm_l40s_qwen3-32b_tp2.json`) and the L40S Vidur/LLMServingSim runs, at its lower measured rate of 2.5 req/s. |

**`run_T1.py` replays these by default.** Fig. 4 is a *controlled*
comparison: MIST, the real vLLM run, Vidur, and LLMServingSim2.0 must all
see the same 100 requests in the same arrival order for overlaying their
latency distributions to mean anything. If MIST instead simulated a
different sample of 100 ShareGPT conversations, its curve and vLLM's curve
would be answering different questions — the "MAE" between them would
mostly measure *how different the two workloads happen to be*, not how
accurate MIST is. Replaying a fixed trace doesn't compromise
reproducibility: the trace file is committed, the arrival schedule it
encodes is deterministic, and MIST's simulation of it is deterministic —
re-running `run_T1.py` reproduces the exact same CSV every time. What the
reproducibility contract actually requires is that MIST's *output* comes
from actually running the simulator (never hand-copied), which is true in
both modes.

### `--resample-sharegpt`: opt-in sensitivity analysis, not a baseline comparison

`run_T1.py --resample-sharegpt` instead draws a fresh, seeded 100-request
sample from the public `ShareGPT_V3_unfiltered_cleaned_split.json`
(fetched by `scripts/download_traces.sh`) and schedules Poisson arrivals
at `--rps`/`--seed`. This is useful for asking "how much does MIST's
predicted latency distribution move if you swap in a different-but-similar
ShareGPT sample" — it is **not** a substitute for the fixed-trace
comparison above, and its output should not be read as a MIST accuracy
number.

We measured this trade-off directly. Replaying `sharegpt_replica_5qps_tpu_h100.csv`
(the fixed trace, default mode) reproduces the real H100 latency
distribution to within ~6.5% mean absolute error (~8.3% for TPU, ~11.5%
for L40S — all far closer to the paper's <2%-ish claim than any resampled
run gets). But `--resample-sharegpt` with `--seed 259` reproduces the same
H100 baseline to only ~277% MAE, and `--seed 7` to ~305% — both stayed
in the same 150-300% range despite very different seeds. This is a
**sensitivity result about workload sampling, not a MIST error**: ShareGPT's
prompt/response length distribution is heavy-tailed, so a random 100-request
draw can carry substantially more (or less) aggregate token demand than the
specific curated sample above at the *same nominal RPS* — enough, for these
particular platform/model combinations, to push the simulated system from
comfortably-loaded into queueing that compounds latency several-fold. Use
`--resample-sharegpt` to explore that sensitivity; use the default mode for
anything you want to compare against the vLLM/Vidur/LLMServingSim numbers
in this directory.

## KNOWN_ISSUES: two upstream bugs found while building T1

Both found and worked around entirely from within `run_T1.py` — no files
in `MIST` or `GenZ` were modified. See
[`docs/FINDINGS.md`](../../../docs/FINDINGS.md#upstream-bugs) for
the full writeup with code and the upstream fix for each:

1. `mist.Engine.LLMEngine`'s mutable `{}` default cache arguments are
   shared across every engine constructed in a process — confirmed to
   silently corrupt multi-platform runs (worked around in `run_T1.py` by
   passing fresh dicts explicitly).
2. GenZ's `GEMMQuantMode.bfloat16` (and FMHA/KVCache/MoE equivalents) no
   longer exist after an upstream aiconfigurator rename, blocking every
   `System(...)` construction (worked around by `_patch_genz_quant_compat`).
